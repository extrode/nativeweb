# 018 — Plan

Spec: [./018-spec.md](./018-spec.md)

## Approach

Documentation is written against the source rather than from memory, and then held there by a
test. That second half is the design decision: `docs/02-reference/configuration.md` is the
cautionary case — 302 lines that were true when written and describe an application that left
the repository, on a page served live at `/docs`. Prose that was checked once decays silently,
so this spec's own output gets a mechanical staleness check in the same branch.

The check is deliberately mechanical rather than semantic. It asserts two things a machine can
know: **every path a document names exists**, and **the configuration keys the documents
declare are the configuration keys the code reads, both ways**. It does not attempt to verify
that a paragraph is true. That boundary is the point — a claim list maintained by hand would
itself go stale, so the checks extract their expectations from the tree at run time.

Alternative considered and rejected: **compiling the README code samples**, by extracting
fenced C# blocks into a generated test project. It is the strongest possible check and it was
rejected on cost and on false failures — a README example is an illustrative fragment with
elided context, and making every one compile would force them into a shape that documents the
compiler rather than the reader. The adoption guide gets the strong treatment instead: its
commands are run end to end against a real scratch application before it is committed.

Placement follows an existing seam. `tests/nativeweb.repo.tests.unit/` already parses sources
and workflows to assert facts about the repository (`ActionPinTests`, `AssetParityTests`), it
has a `RepoRoot()` helper, and it runs in every `dotnet test`. Documentation staleness is a
repository fact, so it lands there rather than in a new Deno tool that nobody would run.

## Tech / dependencies

None added. xUnit in the existing `nativeweb.repo.tests.unit` project; `scripts/build-docs.sh`
and `tools/docs-site/check.ts` already exist and are used as they are.

## Data / interfaces

The configuration surface is one method: `NativeWebOptions.TryFromConfiguration`
(`libs/nativeweb.web/NativeWebOptions.cs:239`) builds every key through a local
`Key(leaf) => $"{prefix}:{leaf}"`. The documented set is therefore extractable from source, and
the parity test does exactly that rather than holding a copy.

| Key (section-relative) | Default | On a bad value |
| --- | --- | --- |
| `Db:ConnectionString` | none | null; app reports not-ready |
| `Db:CommandTimeoutSeconds` | none | ignored unless a positive int |
| `Db:MaxAutoPrepare` | 20 | falls back to 20 |
| `ForwardedHeaders:KnownProxies` | empty | unparseable entries skipped, not fatal |
| `Telemetry:Enabled` | false | **fails startup**, key named |
| `DataProtection:KeyDirectory` | under the user's home | **fails startup** if unwritable and no usable home |
| `BotTraps:MinAgeSeconds` | none | **fails startup** if not a non-negative number |
| `RateLimit:General:PermitLimit` | 120 | falls back to 120 |
| `RateLimit:CspReport:PermitLimit` | 10 | falls back to 10 |
| `Readiness:CacheSeconds` | 1 s | clamped to 30 s max |
| `SecurityContact` | unset, serves no `/security.txt` | **fails startup** if unnormalisable |

Root-level, outside the section: `OTEL_SERVICE_NAME` (defaults to the application name),
`OTEL_EXPORTER_OTLP_ENDPOINT`, and `ConnectionStrings:{section}` — which `apps/sample`
(`Program.cs:42`) prefers over `{section}:Db:ConnectionString`.

## Risks & mitigations

- **A README is wrong the day after it is written.** The path and parity tests catch renames and
  key drift; they cannot catch a prose claim that was never true. Mitigated by writing each
  README from its own source files in the same pass, and by the two-lens review before merge
  carrying R4 as an explicit question.
- **The parity test is too strict and blocks unrelated work.** A new `Key(...)` in
  `NativeWebOptions` would fail the suite until documented. That is the intended cost and it is
  small — one table row — but it is a real coupling and the test says so in its own message.
- **Delegated prose drifts from house style.** The five delegated READMEs are reviewed and
  corrected inline before commit; the dispatch carries the banned-words table and names the
  source files it may read and nothing else.
- **The adoption probe leaves scratch.** `tmp/adopt-probe/` is own-scratch under the project's
  own `tmp/`, removed directly rather than scripted.
- **No security or data exposure surface.** This spec adds no code path, no input handling and
  no external call. `DocsClaimsTests` reads files under the repository root only.
