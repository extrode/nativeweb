# Plan — xunit 2.9.3 → xunit.v3 4.0.0

Standard tier. Branch: `chore/xunit-v3`.

## Context

Every test project in the repo is on `xunit` 2.9.3 with `xunit.runner.visualstudio` 3.1.5 and
`Microsoft.NET.Test.Sdk` 18.7.0, driven by VSTest through `dotnet test`. The user asked to move to
the current major, 3.x.

**The upgrade is not a pin bump — it forces a runner change**, and that is the whole reason this
needs approval before it is built. Measured this session against a throwaway project under
`tmp/xunit3-probe`, on SDK 10.0.203:

| fact | measured |
|---|---|
| `xunit.v3` 4.0.0 depends on `xunit.v3.mtp-v2` → `Microsoft.Testing.Platform` 2.3.3 | from the `.nuspec` |
| a v3 project under the old `dotnet test` | `error : Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later` |
| the same, with `Microsoft.NET.Test.Sdk` 18.7.0 + `xunit.runner.visualstudio` 4.0.0 added | identical error — **VSTest is not an available option** |
| opt-in is `global.json` → `"test": { "runner": "Microsoft.Testing.Platform" }` | `dotnet test --help` says so; it works |
| a v3 test project must set `<OutputType>Exe</OutputType>` itself | `error : xUnit.net v3 test projects must be executable ... If this is not a test project, reference xunit.v3.extensibility.core instead` |
| `dotnet test <path>` | rejected: `Specifying a project for 'dotnet test' should be via '--project'` |
| `--nologo` | not a recognised option; it is forwarded to the test app, which then runs nothing and exits 5 |
| `-v q` | still accepted |
| `--filter "FullyQualifiedName!~Readyz"` | works unchanged (VSTest filter syntax is preserved as `--filter`) |
| a filter matching nothing | `Zero tests ran`, **exit 8** — no longer a silent green |

So: `Microsoft.NET.Test.Sdk` and `xunit.runner.visualstudio` are dropped, not upgraded, and every
`dotnet test <path> --nologo` in the repo becomes `dotnet test --project <path>`.

## Changes by area

**Pins.** `Directory.Packages.props` — drop `xunit`, `xunit.runner.visualstudio`,
`Microsoft.NET.Test.Sdk`; add `xunit.v3` 4.0.0 and `xunit.v3.extensibility.core` 4.0.0. Same three
lines for `skeleton/Directory.Packages.props`.

**Runner opt-in.** `global.json` and `skeleton/global.json` gain the `test.runner` section. Without
it every `dotnet test` in the repo fails at the MSBuild target, so this is the first commit.

**The 20 test projects under `tests/`.** One pattern, repeated: add `<OutputType>Exe</OutputType>`
and replace the three `PackageReference`s with a single `<PackageReference Include="xunit.v3" />`.
Representative: `tests/nativeweb.repo.tests.unit/…csproj`,
`tests/nativeweb.sample.tests.integration/…csproj`, `tests/nativeweb.scaffold.tests.e2e/…csproj`.
The two nested hosts (`…tests.integration/public-read-host`, `…tests.aot/probe-host`) carry no
xunit reference and are untouched.

**`libs/nativeweb.signin.testing`.** This is packable and `DevelopmentDependency=true`; it holds
abstract conformance suites a consumer derives from, so it must not become an executable.
`xunit` → `xunit.v3.extensibility.core`, which is the package the v3 build error names for exactly
this case. `IsTestProject=false` and the comment explaining it stay.

**~13 `IAsyncLifetime` implementations.** v3 changes both members to `ValueTask`. Mechanical
`Task` → `ValueTask` on `InitializeAsync`/`DisposeAsync`, in e.g.
`tests/nativeweb.scaffold.tests.e2e/BrowserFixture.cs`,
`tests/nativeweb.web.tests.unit/NegotiatedCacheTests.cs`,
`skeleton/tests/__product__.tests.e2e/BrowserFixture.cs`. Types that already implement
`IAsyncDisposable` with `async ValueTask DisposeAsync()` need nothing.

**CI.** `.github/workflows/ci.yml` (7 steps), `.github/workflows/publish.yml` (1),
`skeleton/.github/workflows/ci.yml` (3): `--project` in, `--nologo` out. The `ciprobe` steps in
`ci.yml` drive a stamped skeleton, so they move with it.
`PackageFeedConfigTests.Workflow_RestoresTheSolutionBeforeTheFirstTestStep` matches the literal
`dotnet test` and survives.

**`tools/stamp-check.ts`.** Both `run("… tests", "dotnet", [...])` calls take `--project` and lose
`--nologo`. `DATABASE_FREE_FILTER` is unchanged. `testsRun()` currently reads `Passed: N` /
`Total tests: N`, which MTP does not print — it prints `succeeded: N` and `total: N`; re-teach it
and update `tools/stamp-check.test.ts` alongside. Its zero-count guard stays, but is now
belt-and-braces: MTP exits 8 on a filter that matches nothing.

**Docs.** `README.md`, `docs/00-quick-start/getting-started.md` (13 lines),
`docs/00-quick-start/tutorial-first-feature.md` (3), `skeleton/README.md` (3).

**A new repo-tier guard**, beside `FrameworkTemplateDeliveryTests`: nothing in the tree references
`xunit` 2.x, `xunit.runner.visualstudio` or `Microsoft.NET.Test.Sdk`; every project that references
`xunit.v3` sets `OutputType=Exe`; both `global.json` files carry the runner opt-in. Reading the
files is legitimate here for the same reason the sibling guards do it — these are facts about build
configuration that no compile or test run would otherwise notice. Falsified by breaking each of the
three, per the usual green → commit → break → `git checkout --` order.

**Visibility.** `CHANGELOG.md` under `## [Unreleased]`, `work/status/current.md`.

## Risks

- **`WebApplicationFactory` without `Microsoft.NET.Test.Sdk` is the one real unknown.**
  `Microsoft.AspNetCore.Mvc.Testing` generates `MvcTestingAppManifest.json` from a target keyed on
  `IsTestProject`, which VSTest's SDK used to set. `Microsoft.Testing.Platform.MSBuild` is expected
  to set it too, but this was not probed. It gates 5 integration tiers, so it is **verified first,
  on `tests/nativeweb.sample.tests.integration`, before any other project is touched.** If it does
  not hold, the fix is an explicit `<IsTestProject>true</IsTestProject>`; if that fails too, the
  branch stops there and reports rather than working around it.
- **`xunit.analyzers` 2.0.0 arrives with `xunit.v3`** and `TreatWarningsAsErrors` is repo-wide, so
  a new analyzer rule is a build failure, not a warning. Expect to fix findings or `NoWarn` them
  with a reason; a bare blanket `NoWarn` is not acceptable.
- **CI cannot prove any of this.** All three jobs are already red on the JauntyQ package `403`
  (`project-jauntyq-ci-gap`), so the workflow edits are reviewed, not exercised.
- Playwright e2e tiers publish and drive a real binary; `OutputType=Exe` on the *test* project is
  new but does not touch the fixture's own publish.
