# 005 — R16 load harness (`tools/bench/`)

## Context

Spec 012 (htmx 2.0.10 → 4.0.0) is merged but not `done`: R16 asked for the §14 benchmark
re-run and nothing reproduces it — the original figures came from two purpose-built apps
load-tested with `wrk` in a sandbox that no longer exists
(`docs/01-architecture/native-web-architecture.md` §14 records this). The user chose the
"commit a load harness" close: a reproducible harness under `tools/` against `apps/web`
itself, with a committed baseline, so R16 becomes re-runnable for every future upgrade.
R16 is restated as **"throughput and RSS within tolerance of `baseline.json`"**.

Constraints that shape the design:
- **No load tool on this machine** — no `wrk`, `bombardier`, `hey`, `oha`, `ab`. Deno 2.9.5
  is present and is the mandated runtime (Deno-never-Node). The driver is therefore written
  in Deno: N concurrent `fetch` workers with keep-alive over a fixed duration. Lower
  absolute ceiling than `wrk`, but the baseline comparison is relative on the same machine,
  which is what R16 needs.
- **Numbers are machine-bound.** `baseline.json` carries a machine fingerprint (hostname,
  logical CPU count, OS); `--check` compares only when the fingerprint matches, otherwise
  records and says so. This mirrors `scripts/ci/publish-budgets.json`'s record-only mode
  for a null budget. The harness is a manual per-upgrade tool, not a CI job — CI runner
  variance would make every threshold a lie.
- **The app boots with no DB** — anonymous `GET /` renders the full page (Layout + CSP
  nonce + antiforgery mint, `apps/web/Program.cs:797`) without touching PostgreSQL, and
  `/healthz` is unlimited. The only knob needed is the page rate limiter
  (`NativeWeb:RateLimit:Page:PermitLimit`, `Program.cs:234`), raised via env var the same
  way `AppProcessFixture` raises the auth limiters.

## Layout (mirrors `tools/audit/` conventions: deno.json, `*.test.ts` beside sources)

```
tools/bench/
  deno.json           # tasks: bench, test
  run.ts              # entry: flag parsing, orchestration, exit codes
  server.ts           # publish + launch + wait-for-healthz + stop lifecycle
  load.ts             # the driver: N workers, keep-alive fetch, fixed duration
  stats.ts            # pure: mean, percentiles, baseline comparison
  rss.ts              # sample WorkingSet64 during load (PowerShell on win, ps on linux)
  baseline.json       # committed figures + machine fingerprint
  README.md           # what it measures, how to re-baseline, why not CI
  *.test.ts           # one per module
```

## Behaviour

- `deno run -A tools/bench/run.ts` — publish `apps/web` Release (skippable with
  `--skip-publish`), launch the published exe from its publish dir
  (`apps/web/bin/Release/net10.0/<rid>/publish/`, same path rule as
  `AppProcessFixture.PublishedExePath`), env:
  `ASPNETCORE_URLS=http://127.0.0.1:5997` (http like `check-publish-budgets.ps1` — no
  cert, and TLS handshake noise is not what R16 measures),
  `ASPNETCORE_ENVIRONMENT=Development`, `NativeWeb__Telemetry__Enabled=false`,
  `NativeWeb__RateLimit__Page__PermitLimit=1000000000`. Wait for `/healthz` 200.
- **Scenarios**: `home` (GET `/`, the full-page render) and `healthz` (the floor, matching
  §14's shape of measuring both the page and the no-render floor). Per scenario: one warmup
  pass discarded, then **3 timed runs of 10 s each, averaged** — §14's own discipline
  ("three runs per test"). Concurrency fixed (16 workers) and recorded in the output.
- **RSS**: max WorkingSet64 observed while load runs, sampled ~4×/s
  (`powershell -NoProfile (Get-Process -Id N).WorkingSet64` on Windows, `ps -o rss=` elsewhere).
- Output: printed table + `tmp/bench/latest.json` (gitignored scratch).
- `--baseline` — rewrite `tools/bench/baseline.json` from this measurement.
- `--check` — compare against `baseline.json`, one-sided: **rps ≥ 95% of baseline, RSS ≤
  105% of baseline**, per scenario. Fingerprint mismatch → print measurement, say the
  baseline is from another machine, exit 0 with a distinct "record-only" note. Regression →
  nonzero exit naming the scenario and both numbers.
- Server always stopped in a `finally`; port conflict and non-200 startup are named errors.

## Tests (same branch)

- `stats.test.ts` — percentiles, averaging, the two-sided-vs-one-sided comparison edges
  (exactly 95%, just under, RSS just over 105%).
- `load.test.ts` — drive against a local `Deno.serve` stub; assert request counting, error
  counting, and that a stub returning 500s is reported as errors not throughput.
- `server.test.ts` — lifecycle against a stub process where cheap; wait-for-healthz timeout
  path.
- `run.test.ts` — flag parsing, fingerprint match/mismatch routing, exit codes.
- Mutation-check per policy: break the comparison operator, confirm the test fails.

## What changed during implementation

- **The harness serves https, not http.** The plan assumed http on loopback like
  `check-publish-budgets.ps1`. `apps/web` cannot render a page over http: the antiforgery
  cookie is `CookieSecurePolicy.Always` and `Layout.Page` mints a token on every page, so
  `GET /` throws and answers 500. Measured on the published binary — the first baseline run
  recorded 245,106 of them. `tools/bench/cert.ts` mints a throwaway CA and leaf with openssl
  into `tmp/bench/`, and the driver trusts that CA alone. A CA plus a leaf rather than one
  self-signed certificate, because Deno's client rejects a trust anchor offered as an end
  entity (`CaUsedAsEndEntity`, also measured).
- **Tolerances are 15% down on throughput and 25% up on RSS, not 5%.** Eight `home` passes on
  one machine and one unchanged binary spread 13.8%, `healthz` 9.4%, peak RSS 24%. A 5% band
  would have failed on noise more often than on a regression.
- **`--baseline` refuses a broken measurement** (failed requests, zero throughput, or no RSS
  reading). The first real run wrote a 0 req/s baseline without complaint, under which the
  floor would have been unfailable forever.
